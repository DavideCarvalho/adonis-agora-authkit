This is the complete happy path: install the packages, write the two config files, mount
the host, wire login / callback / logout, and read the authenticated user in your
controllers. By the end you have a working IdP **and** a relying party that knows who's
logged in.

If you want the two end-to-end topology walkthroughs side by side (everything-in-one-app
vs. a standalone IdP with separate client apps), see the [Quickstart](/docs/starter)
instead — this page is the linear single-app path.

## Install & scaffold

Use `node ace add` — it installs the package **and** runs its configure hook in one step.
Run it once per package:

```bash
node ace add @adonis-agora/authkit-server
node ace add @adonis-agora/authkit-client
```

<Callout type="info">
  AuthKit needs a SQL connection for its adapter and stores. The `database` adapter and
  `lucidAccountStore` use Lucid, so `@adonisjs/lucid` must be installed and configured.
</Callout>

### What the server `add` scaffolds

`node ace add @adonis-agora/authkit-server` prompts for the UI preset of the
login/consent screens — **`edge` | `react` | `headless`** (pass `--ui=react` to skip the
prompt) — and then:

- Publishes **`config/authkit.ts`** — a starter config (Redis adapter, managed JWKS,
  `lucidAccountStore(AuthUser)`). Edit it to taste.
- Publishes the **`app/models/auth_user.ts`** model, composed from the `withAuthUser()` +
  `withCredentials()` mixins.
- Registers the **provider** in `adonisrc.ts` and the bundled **ace commands** (including
  `authkit:eject`) via the package's `adonisjs` block.
- Adds an **env validation** for `AUTHKIT_ISSUER` and writes a default value
  (`http://localhost:3333/oidc`) to `.env`.

**What each `--ui` preset does:**

| Preset | UI files published | Render mode |
| --- | --- | --- |
| `edge` (default) | None | Built-in Edge views from the `authkit::` disk — zero setup, works out of the box |
| `react` | React pages under `inertia/pages/authkit/` (login, signup, consent, forgot, reset, verify-email, mfa-challenge, account/login, account/tokens, account/mfa) + `auth_shell.tsx` | `inertiaRenderer({ prefix: 'authkit', views: [...] })` pre-configured in the published config |
| `headless` | None | No render key; flows respond with JSON contracts for you to drive |

<Callout type="info">
  The lib does **not** ship `.tsx` React files — there are no pre-built React pages inside
  the npm package. With `--ui=react` the scaffold **writes starter pages into your project**;
  they are yours to edit from that moment on. With `edge` or `headless`, the authentication
  flow screens are served from the package's built-in Edge views (`authkit::` disk) and
  your project disk has nothing extra.
</Callout>

<Callout type="warn">
  Choosing `--ui=react` requires `@adonisjs/inertia` + `react` + Vite already configured in
  the app, or the command aborts. Run `node ace add @adonisjs/inertia` (with React) first.
</Callout>

#### Tune the server config (manual)

The published `config/authkit.ts` is a Redis-adapter starter. For the Lucid-backed
single-app path in this guide, edit it to use the `database` adapter, point at the
`AuthUser` store, and set the `mountPath`/renderer. **Clients are no longer declared
here** — create them in the admin console after first boot (see below):

```ts title="config/authkit.ts"
import env from '#start/env'
import AuthUser from '#models/auth_user'
import {
  defineConfig,
  adapters,
  lucidAccountStore,
  inertiaRenderer,
} from '@adonis-agora/authkit-server'

const authServerConfig = defineConfig({
  issuer: env.get('AUTHKIT_ISSUER'),
  adapter: adapters.database({ connection: 'auth' }),
  jwks: { source: 'managed', algorithm: 'RS256' },
  ttl: { accessToken: '15m', refreshToken: '30d' },
  accountStore: lucidAccountStore(AuthUser),
  mountPath: '/oidc',
  // React preset: point at the pages written into your project by `node ace add --ui=react`.
  // The `views` list is an allowlist; screens not listed here fall back to Edge views.
  // Remove the `render` key entirely if you chose --ui=edge (built-in Edge views, no setup).
  render: inertiaRenderer({
    prefix: 'authkit',
    views: [
      'login', 'consent', 'signup', 'forgot', 'reset',
      'verify-email', 'mfa-challenge',
      'account/login', 'account/tokens', 'account/mfa',
    ],
  }),
  admin: { enabled: true, authorize: () => true }, // the admin console (React SPA); `authorize` is required in production
  adminApi: {
    enabled: true,
    apiKeys: [env.get('AUTHKIT_ADMIN_API_KEY')],
  },
})

export default authServerConfig
```

The `issuer` is the public URL of the provider and **must end with `mountPath`** — e.g.
`https://auth.example.com/oidc` for `mountPath: '/oidc'`. The published model already
composes the mixins the Lucid store needs; add columns to it as your domain grows.

<Callout type="info">
  **Clients are not part of the config.** The server starts with zero clients; you register
  your first client through the admin console or the Admin API after the first
  start (see [Registering your first client](#registering-your-first-client)).
</Callout>

### What the client `add` scaffolds

`node ace add @adonis-agora/authkit-client` wires `ctx.auth` to the AuthKit session:

- Installs **`@adonisjs/auth`** when the app does not depend on it yet (it is a required peer;
  pass `--no-install` to print the install command instead).
- Publishes **`config/authkit_client.ts`** — issuer, client credentials, and a JWT resolver
  reading the token set from the session.
- Publishes **`config/auth.ts`** with an [`authkitClientGuard`](/docs/adonis-auth) backed by
  `sessionUserProvider` and your user model (`--model=#models/app_user`, default
  `#models/user`). An existing `config/auth.ts` is left alone; the command prints the guard to
  add to it.
- Publishes **`app/middleware/auth_middleware.ts`** (redirects guests to `/auth/login`) and
  **`app/middleware/silent_auth_middleware.ts`** (calls `ctx.auth.check()`), and registers them
  as the named `auth` and `silentAuth` middleware.
- Registers the **providers** (`@adonisjs/auth/auth_provider` and the AuthKit client provider)
  in `adonisrc.ts`.
- Registers **`initialize_auth_middleware`** and **`authkit_context_middleware`** as
  router-global middleware — together they give every request `ctx.auth` and `ctx.authkit`.
- Publishes the **`app/controllers/oidc_session_controller.ts`** stub — the login / callback /
  logout flow written out by hand, for when you need to customise it. You don't need it if you
  use `registerOidcClient` (below).
- Adds **env validations** for `AUTHKIT_ISSUER`, `AUTHKIT_CLIENT_ID`,
  `AUTHKIT_CLIENT_SECRET`, and `AUTHKIT_REDIRECT_URI`. It does **not** write their values —
  fill them in `.env` yourself (see [Environment variables](#environment-variables)).

The remaining client work is manual: tune the config below, and wire the login / callback /
logout **routes** with one `registerOidcClient(router)` call (see
[Login, callback, logout](#login-callback-logout)).

## Client config

Edit the published `config/authkit_client.ts` to declare the issuer, client credentials,
the resolver, and how to map an IdP identity to your user record:

```ts title="config/authkit_client.ts"
import env from '#start/env'
import { defineConfig, lucidMirror, resolvers } from '@adonis-agora/authkit-client'
import AppUser from '#models/app_user'

const authkitClientConfig = defineConfig({
  issuer: env.get('AUTHKIT_ISSUER'),
  clientId: env.get('AUTHKIT_CLIENT_ID'),
  clientSecret: env.get('AUTHKIT_CLIENT_SECRET'),
  redirectUri: env.get('AUTHKIT_REDIRECT_URI'),
  resolver: resolvers.jwt({ tokenSource: 'session' }),

  // Creates the local row on the first login and keeps it in sync on the next ones.
  resolveUser: lucidMirror(AppUser, {
    sync: (identity) => ({ email: identity.email, fullName: identity.profile?.name ?? null }),
  }),
})

export default authkitClientConfig
```

`config/auth.ts` points the guard at the same model. The guard takes its user from
`resolveUser` first, so `lucidMirror` provisions the row on a first login and `ctx.auth.user`
is the row it returned. The model's primary key must be the IdP's `sub`, which is what
`lucidMirror` writes:

```ts title="config/auth.ts"
import { defineConfig } from '@adonisjs/auth'
import { sessionUserProvider } from '@adonisjs/auth/session'
import type { InferAuthenticators } from '@adonisjs/auth/types'
import { authkitClientGuard } from '@adonis-agora/authkit-client/auth'

const authConfig = defineConfig({
  default: 'web',
  guards: {
    web: authkitClientGuard({
      provider: sessionUserProvider({ model: () => import('#models/app_user') }),
    }),
  },
})

export default authConfig

declare module '@adonisjs/auth/types' {
  export interface Authenticators extends InferAuthenticators<typeof authConfig> {}
}
```

No local user table? Use `authkitIdentityProvider()` as the provider and `ctx.auth.user` is the
AuthKit identity itself — see [AdonisJS auth](/docs/adonis-auth#choosing-a-user-provider). For
the `Identity` shape, the resolvers, and reconciling pre-existing rows by email, see
[Client](/docs/client).

## Mount the host (manual)

`registerAuthHost` is **not** scaffolded — add it yourself. It mounts everything in one call — the OIDC provider wildcard, the login /
consent / signup interaction pages, password reset, the account console, and (opt-in)
social, PAT introspection, and rate-limit middleware.

```ts title="start/routes.ts"
import router from '@adonisjs/core/services/router'
import { registerAuthHost } from '@adonis-agora/authkit-server'

registerAuthHost(router, {
  mountPath: '/oidc',
  // social: { providers: ['google'] }, // opt-in
  // rateLimit: { enabled: true },       // opt-in
})
```

<Callout type="info">
  `registerAuthHost` reads the resolved `config/authkit.ts` that the provider stashed at
  boot, so `registerAuthHost(router)` with no options already picks up your `mountPath`,
  `social`, `rateLimit`, `admin` and `adminApi`. The options argument exists to override
  **structural** choices — where things mount. Policy switches you declared in
  `defineConfig` are **locked**: passing them here is ignored and warned about at boot, so
  `config/authkit.ts` stays auditable without reading `start/routes.ts`. See
  [Config locks](/docs/config-locks).
</Callout>

<Callout type="warn">
  **If your app uses `@adonisjs/shield`** (on by default in the `web` starter kit), its CSRF
  protection intercepts the OIDC provider's own machine-to-machine routes mounted above —
  `POST {mountPath}/token` in particular. Without an exemption, `exchangeCode()` gets
  shield's HTML CSRF-denial page back instead of a JSON token response
  (`SyntaxError: Unexpected token '<' ... is not valid JSON`). Use the exported
  `authkitCsrfExceptions` helper in `config/shield.ts` — it stays in sync with whatever
  `mountPath` you pass to `registerAuthHost`/`defineConfig`, so you don't have to hand-write
  the route-pattern regex yourself:

  ```ts title="config/shield.ts"
  import { defineConfig } from '@adonisjs/shield'
  import { authkitCsrfExceptions } from '@adonis-agora/authkit-server'

  export default defineConfig({
    csrf: {
      enabled: true,
      exceptRoutes: (ctx) =>
        authkitCsrfExceptions(ctx.request.url(), { mountPath: '/oidc' }),
    },
    // ...rest of your shield config
  })
  ```

  This exempts only the IdP's OIDC protocol surface (`{mountPath}/*`), the PAT
  introspection endpoint, and the client's back-channel logout route — the interactive
  login/consent/signup pages (under `/auth/interaction/*`) are a **different** prefix and
  keep full CSRF protection. See [Reference](/docs/reference) for the full option list.
</Callout>

## The middleware (already registered)

**`node ace add` already registered the middleware** in `start/kernel.ts`. For reference, it
looks like this:

```ts title="start/kernel.ts"
router.use([
  // ...existing middleware
  () => import('@adonisjs/auth/initialize_auth_middleware'),
  () => import('@adonis-agora/authkit-client/authkit_context_middleware'),
])

export const middleware = router.named({
  // ...existing named middleware
  auth: () => import('#middleware/auth_middleware'),
  silentAuth: () => import('#middleware/silent_auth_middleware'),
})
```

- `initialize_auth_middleware` creates `ctx.auth` (`@adonisjs/auth`).
- `authkit_context_middleware` refreshes the token set when it is about to expire (see
  [Refresh Tokens](/docs/refresh-tokens)) and puts the AuthKit authenticator on `ctx.authkit`.
  The guard and `ctx.authkit` share it, so the session is resolved once per request.
- `auth` requires a session on a route; `silentAuth` checks it without requiring it.

## Login, callback, logout

Login is OIDC authorization-code + PKCE, and the client package ships the whole flow.
Register it with one call (the `/auth/callback` path is the `redirectUri` you registered for
the client):

```ts title="start/routes.ts"
import router from '@adonisjs/core/services/router'
import { registerOidcClient } from '@adonis-agora/authkit-client'

registerOidcClient(router, {
  redirects: { byGlobalRole: { ADMIN: '/admin' }, default: '/' },
})
```

That registers `GET /auth/login` (`auth.login`), `GET /auth/callback` (`auth.callback`),
`POST /auth/logout` (`auth.logout`) and `POST /auth/backchannel-logout`.

The sequence: `/auth/login` redirects the browser to the IdP's `/authorize`; the user
authenticates there and is bounced back to `redirectUri` with `code` + `state`; the callback
verifies `state`, swaps the code for a token set, validates the id_token, and stores it with
`startSession(ctx, tokenSet)`. **The stored token set is the login** — there's nothing else
to persist on the RP. `/auth/logout` ends the local session with `endSession(ctx)` and then
the IdP one (RP-initiated logout). See [Client](/docs/client#the-login--callback--logout-flow)
for every option, [Security](/docs/security#rp-initiated-logout) for the end-session details,
and [Back-Channel Logout](/docs/back-channel-logout) for IdP-initiated termination.

### Owning the flow: the scaffolded controller

When the generated routes do not fit, `node ace add` also published
`app/controllers/oidc_session_controller.ts` — the same flow in three short methods over the
injected `AuthkitClientManager`. Wire it instead of `registerOidcClient`:

```ts title="start/routes.ts"
const OidcSessionController = () => import('#controllers/oidc_session_controller')

router.get('/auth/login', [OidcSessionController, 'login']).as('auth.login')
router.get('/auth/callback', [OidcSessionController, 'callback']).as('auth.callback')
router.post('/auth/logout', [OidcSessionController, 'logout']).as('auth.logout')
```

<Callout type="warn">
  When you edit it, keep going through the manager: `startSession(ctx, tokenSet)` in the
  callback and `endSession(ctx)` in the logout — never a raw `session.put(sessionKey)` /
  `session.forget(sessionKey)`. Only those two clear a parked
  [impersonation](/docs/impersonation) credential, so a raw write lets the actor's refresh
  token outlive the session that stashed it. The scaffolded `logout` is local-only; the
  RP-initiated version and the back-channel route are yours to add — see
  [Client](/docs/client#escape-hatch-build-your-own-flow).
</Callout>

## Registering your first client

After the first boot, open the admin console at `/admin/clients` (log in with an account
that has the `ADMIN` role) and click **Create client**. Alternatively, use the Admin REST
API directly — no browser session required:

```bash
# Create a confidential client for your app
curl -X POST http://localhost:3333/api/authkit/v1/clients \
  -H "Authorization: Bearer $AUTHKIT_ADMIN_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
        "clientId": "my-app",
        "redirectUris": ["http://localhost:3333/auth/callback"],
        "postLogoutRedirectUris": ["http://localhost:3333/"],
        "grantTypes": ["authorization_code", "refresh_token"],
        "tokenEndpointAuthMethod": "client_secret_basic"
      }'
```

The response includes `clientSecret` — **save it now**, it is not recoverable afterwards:

```json
{ "clientId": "my-app", "clientSecret": "s3cr3t-shown-once" }
```

Set the credentials in `.env` and wire them into your client config:

```dotenv title=".env"
AUTHKIT_CLIENT_ID=my-app
AUTHKIT_CLIENT_SECRET=s3cr3t-shown-once
AUTHKIT_REDIRECT_URI=http://localhost:3333/auth/callback
```

From this point the client is stored in the adapter/DB and survives restarts. You can
update its redirect URIs, regenerate its secret, or delete it at any time from the console
or API — no config change or redeploy required.

## Using it in controllers

This is the part you'll use every day. `ctx.auth` is the `@adonisjs/auth` authenticator,
backed by the AuthKit session: `middleware.auth()`, `auth.user`, `auth.getUserOrFail()` and
Bouncer all work as in any AdonisJS app.

### Protecting routes

```ts title="start/routes.ts"
import router from '@adonisjs/core/services/router'
import { middleware } from '#start/kernel'

const DashboardController = () => import('#controllers/dashboard_controller')
const SettingsController = () => import('#controllers/settings_controller')

router
  .group(() => {
    router.get('/dashboard', [DashboardController]).as('dashboard')
    router.get('/settings', [SettingsController]).as('settings')
  })
  .prefix('/app')
  .as('app')
  .use(middleware.auth())
```

Guests are redirected to `/auth/login` (the `redirectTo` of `app/middleware/auth_middleware.ts`),
which starts the OIDC login.

### Reading the user

Behind `middleware.auth()`, `auth.getUserOrFail()` returns your user. It is synchronous and
never `null` there:

```ts title="app/controllers/dashboard_controller.ts"
import type { HttpContext } from '@adonisjs/core/http'

export default class DashboardController {
  async handle({ auth, inertia }: HttpContext) {
    const user = auth.getUserOrFail()
    return inertia.render('dashboard', { email: user.email })
  }
}
```

On pages that also serve guests, put `middleware.silentAuth()` on the route and read
`auth.user`, which is `undefined` for a guest:

```ts title="app/controllers/home_controller.ts"
import type { HttpContext } from '@adonisjs/core/http'

export default class HomeController {
  async handle({ auth, inertia }: HttpContext) {
    return inertia.render('home', { user: auth.user ?? null })
  }
}
```

```ts title="start/routes.ts"
router.get('/', [HomeController]).use(middleware.silentAuth())
```

Authorization goes through Bouncer or [`@adonis-agora/authz`](https://www.npmjs.com/package/@adonis-agora/authz)
as usual — the guard user is the one your policies receive.

### AuthKit-only data — `ctx.authkit`

`ctx.authkit` sits next to `ctx.auth` and carries what only AuthKit knows: the raw identity
(the OIDC claims), the IdP's global roles, the active organization, and the props for the
React package. It is present on every request, public routes included, and never throws on an
anonymous one.

**Identity vs User.** The **Identity** is the OIDC claims, app-agnostic (`userId` = `sub`,
`email`, `globalRoles`, `profile`, `sessionId`, `raw`), the same shape for every resolver. The
**User** is your model — `auth.user`, which is also what `await ctx.authkit.getUser()` returns.

```ts title="app/controllers/admin/overview_controller.ts"
import type { HttpContext } from '@adonisjs/core/http'

export default class OverviewController {
  async handle({ auth, authkit, inertia, response }: HttpContext) {
    const user = auth.getUserOrFail()
    if (!authkit.hasGlobalRole('ADMIN')) return response.forbidden()

    const identity = await authkit.getIdentity()
    return inertia.render('admin/overview', { user, sessionId: identity?.sessionId })
  }
}
```

`hasGlobalRole(role)` is **synchronous** and reads the identity that has already been
resolved — behind `middleware.auth()` or `middleware.silentAuth()` it has been. In a route with
neither, call `await authkit.check()` first.

<Callout type="info">
  **AuthKit authenticates; it does not authorize.** A global role is a coarse, IdP-wide fact —
  "this person is a platform admin" — carried in the token so every relying party sees the
  same answer. For "can this user update *this* post", use
  [`@adonis-agora/authz`](https://www.npmjs.com/package/@adonis-agora/authz) or Bouncer. An
  external role authority can also become the source of the `globalRoles` claim itself, via
  `resolveTokenRoles` on the server. See
  [Customizing auth](/docs/customizing-auth#where-roles-come-from-resolvetokenroles).
</Callout>

<Callout type="info">
  **`globalRoles` needs the `roles` scope.** The provider binds the roles claim to that
  scope, so a client only receives roles when it asks for it — which the client kit's
  default scopes already do. If you register clients you do not own, restrict the claim
  further with `firstPartyClients` in `config/authkit.ts`; see
  [The roles claim](/docs/customizing-auth#the-roles-claim).
</Callout>

### Hand the session to the frontend — `toSharedProps()`

If your UI uses `@adonis-agora/authkit-react`, its `useAuth()` reads a single Inertia shared
prop named `authkit`. `toSharedProps()` builds exactly that object — `{ user, globalRoles }`,
or `null` when there is no session:

```ts title="config/inertia.ts"
sharedData: {
  authkit: (ctx) => ctx.authkit.toSharedProps(),
},
```

[React](/docs/react) covers the frontend half.

### Typing the user

`auth.user` is typed by your provider's model. To type `ctx.authkit.getUser()` the same way,
declare it once:

```ts title="types/authkit.ts"
import type AppUser from '#models/app_user'

declare module '@adonis-agora/authkit-client' {
  interface AuthkitUserType {
    user: AppUser
  }
}
```

That's the whole single-app setup — provider, relying party, `ctx.auth` and `ctx.authkit` all
wired. Continue with [Topologies](/docs/topologies) to decide how to deploy it,
[AdonisJS auth](/docs/adonis-auth) for the guard and API routes,
[Account Store](/docs/account-store) to point AuthKit at your user table,
[Client](/docs/client) for the deeper resolver model, or
[Customizing auth](/docs/customizing-auth) for recipes on role gating, custom screens,
emails, and events.
